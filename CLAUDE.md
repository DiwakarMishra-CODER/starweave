# Starweave — context handoff

## What it is

Starweave is an interactive force-directed graph that maps influence relationships between indie, shoegaze, dream-pop, electronic, folk/confessional, emo/post-hardcore, post-rock/drone/noise, and American-underground artists, rooted at The Velvet Underground. Users explore a constellation of **297 artists** split across seven realms — `core` (5 foundational artists: Velvet Underground, Kraftwerk, Can, Neu!, Brian Eno), `region-one` (**72** artists: the British post-punk→shoegaze→dream-pop spine, modern UK/Windmill bands, proto-punk roots, and a 2026 extension pass that closed a ~27-artist gap in the original roster — see Current state below), `electronic` (**59** artists across 8 electronic lineages, similarly extended), `folk-confessional` (**50** artists across 5 folk lineages), `emo-posthardcore` (**30** artists across 4 lineages: hardcore-roots/post-hardcore/midwest-emo/math-rock), `post-rock-drone-noise` (**23** artists across 3 lineages: post-rock/no-wave/drone — down from 23 once `a-silver-mt-zion` was pulled for having zero edges, see Current state), and `american-underground` (**58** artists across 5 lineages: noise-alt/college-rock/indie-rock/psych/neo-psych, split out of region-one) — click any node to open a slide-over artist panel, and navigate to full artist detail pages with bios, major-album cards (cover art + 3–4 sentence write-up — the UI section reads "Major album"; the underlying field is still `classicAlbums`), and influence chips. Region-one and core nodes are colored by the original five `Layer` values (root → post-punk → shoegaze/dream-pop → indie-alt → outside); every other realm is colored per-lineage instead, each realm owning its own distinct hue family (see Design system below). The aesthetic is atmospheric — dark background, nebula/grain layer, realm/layer-keyed glow colors. **1,048 edges — 902 cited (556 first-person, 224 reported, 122 critic), 146 `unsourceable`, and as of Aug 2026 zero `unchecked` — plus 30 recorded `rejectedEdges` denials, 53 genre ids, 14 scenes** — verify all of these directly (see the command just below) before trusting them, this doc drifts fast.

**Artist and edge counts in this doc will drift out of date fast — this graph is under active, frequent expansion.** Before quoting a count anywhere (a realm size, an edge total, a genre list), verify it directly: `npx tsx -e "import { graphData } from './data/seed-data'; console.log(graphData.artists.length, graphData.edges.length)"` — cheaper and more reliable than trusting the last session's number.

**Stack:** Next.js 16 App Router · TypeScript · `react-force-graph-2d` (canvas) · static JSON data build · no database.

## Architecture decisions

**Persistent graph layout.** The graph lives in `app/(graph)/layout.tsx` as a shell that never unmounts. Artist pages (`/artist/[slug]`) are rendered inside that shell so the force simulation stays alive across navigation. The graph uses a Client Component; artist pages are Server Components.

**Static data pipeline.** Source of truth is `data/seed-data.ts` (hand-curated artists, edges, major albums — field name `classicAlbums`). At build time, `scripts/build-graph.ts` enriches it — fetching artist images (Deezer) and album cover art (iTunes `artworkUrl100` → `600x600bb`) — and writes `public/graph.json`. At request time, `lib/graph-data.ts` reads that file with a module-level cache (`let _cache`). **Restart the dev server whenever `public/graph.json` is patched** to bust the cache.

**Influence score.** Computed as in-degree of influence edges (how many artists in the graph cite this artist as an influence). Used to scale node radius.

**Realm separation forces.** `components/graph/ForceGraph.tsx`'s `presettleLayout` (run once, synchronously, before `ForceGraph2D` ever mounts — see Zoom-based cloud/detail reveal below for why) places core at dead center and spaces every other realm on an ellipse (`computeRealmHomePositions`, `REALM_RADIUS_X/Y = 260/165` — raised from the original `230/145` once cloud-zoom density tuning showed the tighter ellipse crowded realms into "petals" around core). Each realm's angle is a named, tunable constant in `REALM_ANGLE_DEG` (0°=right, 90°=below, 180°=left, 270°=above) rather than pure auto-spacing, so adding a realm can't silently shift the existing ones' positions — current layout is exact 60° spacing, same adjacency order as the original uneven layout: `electronic` 0°, `folk-confessional` 60°, `american-underground` 120°, `region-one` 180°, `post-rock-drone-noise` 240°, `emo-posthardcore` 300°. Any realm NOT listed in `REALM_ANGLE_DEG` falls back to even auto-spacing among just the other unlisted realms. `forceX`/`forceY` pull each node toward its realm's point (`REALM_PULL_STRENGTH = 0.6`, isotropic; core gets its own stronger `CORE_PULL_STRENGTH = 1.2` so it isn't dragged into region-one's mass by its own heavy edges), realm-tagged nodes get weaker mutual repulsion (`REALM_CHARGE = -22` vs the default `-40`) so each realm's bloom can pull tighter, and link strength is weakened on cross-realm ("bridge") edges relative to within-realm edges. A hand-rolled collision force (`createCollideForce`, positional not velocity-only, `COLLIDE_ITERATIONS = 3` passes/tick) keeps nodes from overlapping even in the densest cluster. A node with no `realm` (there are none among real artists anymore, since `data/seed-data.ts` backfills every artist without an explicit `realm` to `core`/`region-one`) is unaffected by any of this. `SCROLL_MIN_ZOOM` (1.6) was never re-verified empirically against the wider `260/165` ellipse — flagged once, never confirmed either way; if the cloud view looks cramped at max zoom-out, check this first.

**Zoom-based cloud/detail reveal.** The graph has two visual modes tied to `globalScale`, both driven from `ForceGraph.tsx`: **cloud/overview** (zoom ≤ `FADE_ZOOM_OUT = 2.5`) and **detail** (zoom ≥ `FADE_ZOOM_IN = 3.5`), crossfading continuously in between (`computeZoomFade`, hub-biased so influential nodes/labels resolve in earlier). User scroll-zoom is clamped to `[SCROLL_MIN_ZOOM, SCROLL_MAX_ZOOM] = [1.6, 7]` (the floor was lowered from 2.5 once six realms plus core no longer fit in view at that zoom — see the `REALM_RADIUS_X/Y` comment in `ForceGraph.tsx`; `FADE_ZOOM_OUT` was deliberately NOT lowered alongside it, since the added headroom below 2.5 is just more room to pull back while already fully in cloud-dot rendering, not a new visual state); the focus/click-to-zoom camera can escape those bounds (declarative `minZoom`/`maxZoom` props swap between a clamped/unclamped tuple via React state — they're not in `react-force-graph-2d`'s imperative ref API, so this can't be done by calling a method).
- **Cloud zoom:** every node draws as a small sharp colored point (size/brightness scaled by `influenceScore`, most nodes faint, hubs brighter + a soft halo), against a near-black background wash (`OVERVIEW_BG_WASH_COLOR`/`_MAX_ALPHA`, painted in raw screen space so it ignores pan/zoom), a per-node additive nebula glow per realm (`CLOUD_BACKDROP_INTENSITY = 0.08`, deliberately dim — flat dark gold for core, no white-hot center), and a decorative dust starfield (`DUST_STAR_COUNT = 450` static, non-interactive points jittered around each realm's home cluster, pure decoration, not in `stableData`). Only edges touching a `core` node render as faint glowing "galaxy arm" threads (`isCoreEdge`, gated `&& edgeFade < 1` so this is structurally cloud-zoom-only, not just a formula that happens to converge); every other edge is a near-invisible floor-opacity web. Only the top `ANCHOR_COUNT = 12` nodes by `influenceScore` get name labels.
- **Detail zoom:** node radius/label `fontSize` are otherwise fixed graph-space values with no zoom term — since `react-force-graph-2d` scales everything (position AND radius) by the same `globalScale`, that meant zooming in never actually opened up relative gaps between nodes. `computeZoomSizeMult` (`ZOOM_SIZE_REFERENCE = 3.5`, `ZOOM_SIZE_DAMPEN = 0.75`) shrinks graph-space radius/font-size relative to the (unchanged) node spacing above the reference zoom — a no-op at/below it. Applied identically in `drawNode` and `paintNodePointerArea` (hit-testing must stay in sync with what's drawn) and to label `fontSize`, always *before* the separate click-focus readability floor so that floor's guaranteed minimum on-screen size is never undercut.
- **Labels:** placed in `onRenderFramePost` after every node's circle is known, with a bump-search collision avoidance (`LABEL_BUMP_MAX_STEPS`/`LABEL_BUMP_STRIDE_MULT`) and a dark rounded "chip" background (`LABEL_CHIP_PAD_X/Y`, `LABEL_CHIP_RADIUS`, `LABEL_CHIP_MAX_ALPHA`, via a small `drawRoundedRect` helper) instead of a text shadow. Forced (persistent hub/anchor) labels are processed highest-`influenceScore`-first and are **hidden entirely** rather than drawn overlapping if no clear spot is found — a lower-influence label always yields to a higher one. Focus/hover/path labels keep the old "accept the overlap" fallback instead, since hiding something the user is actively pointing at would be worse.
- **Edges:** arrowheads (`linkDirectionalArrowLength`/`RelPos`/`Color` props) only render on focused/hovered/genre-set-highlighted edges; the resting web (including path-find mode) is plain lines, no arrowheads.
- **Perf:** `autoPauseRedraw={false}` (needed because cloud-zoom brightness is continuously zoom-dependent) makes the canvas repaint every frame regardless of physics state, so every radial-gradient glow (nebula, bloom haze, cloud dot) is pre-rendered once into a cached offscreen-canvas sprite and reused via `drawImage` + `globalAlpha`/scale — never reconstruct a `CanvasGradient` per node per frame, that's what caused a severe lag regression the one time it slipped in.

**Realm/lineage color model.** `lib/colors.ts` defines `LAYER_COLORS` (5 hex values, one per `Layer`) plus a second, orthogonal axis layered on top: one `*_LINEAGE_COLORS` map per non-core, non-region-one realm — `LINEAGE_COLORS` (electronic, 8 hues, magenta/pink-purple), `FOLK_LINEAGE_COLORS` (folk-confessional, 5 hues, yellow-green/olive), `EMO_LINEAGE_COLORS` (emo-posthardcore, 4 hues, red/crimson), `POSTROCK_LINEAGE_COLORS` (post-rock-drone-noise, 3 hues, purple/violet), `AMERICAN_UNDERGROUND_LINEAGE_COLORS` (american-underground, 5 hues, amber/orange/rust) — plus a shared `CORE_COLOR` (reuses `LAYER_COLORS.root`). Every family is deliberately kept at a different hue range from every other (see Design system below) so realms never read as ambiguous with each other at a glance. Everything reads through resolver functions — `resolveNodeColor` / `resolveNodeGlow` / `resolveEdgeTint` / `resolveNodeLabel` — that branch on `node.realm`: no `realm` → `LAYER_COLORS[layer]` (this is the only branch any region-one node takes, keeping its rendering byte-for-byte unchanged from before the realm system existed), `realm === 'core'` → `CORE_COLOR`, every other known realm → its own per-`lineage` hex via a small `xColor(lineage)` helper with a defensive default. Adding a new realm's branch is always additive: a new `if (node.realm === '...')` line inserted before the final region-one fallback in each of the four resolvers, never a change to the existing branches. These feed node fills, artist page backgrounds (`--layer-color`), album card hover glows, and influence chip borders (`--chip-color`).

**Every content route lives inside the `(graph)` route group now — `/artist/[slug]`, `/genre/[genre]`, `/scene/[scene]`, and `/browse`.** `app/(graph)/layout.tsx` renders `<GraphView>` once, unconditionally, with `{children}` swapped underneath it; any route inside the group shares that persistent mount instead of triggering a fresh one. `/genre`, `/scene`, and `/browse` all used to live outside the group — each one's first-ever navigation into `/artist/[slug]` (or vice versa) crossed a route-group boundary, forcing Next.js to mount `(graph)/layout.tsx` (and therefore `GraphView`'s ~293-node, 300-tick `presettleLayout`) from scratch, which is what a ~5 second navigation delay traced back to twice (once for genre/scene, once for browse). The fix each time was the same three-step move: relocate the page file into `app/(graph)/...`, wrap its content in a fixed/`inset:0`/`z-index:50`/opaque overlay div if it didn't already have one (`.genre-overlay`/`.artist-overlay`/`.browse-overlay` in `app/globals.css` — required, since the persistent `GraphView` canvas now sits underneath at all times and would otherwise show through), and extend `GraphView.tsx`'s `isBackgrounded` pathname check to also match the new route prefix so the canvas stops its per-frame redraw while that page covers it. **Any future top-level content page needs the same three-step treatment before it's considered done** — a page that "just works" outside the group is actually leaving this specific perf bug on the table for its first cross-navigation.

**Genre/scene highlight ("set mode") is a second, parallel highlight system alongside click-focus, not a variant of it** — driven by `highlightSetIds` (the member artist ids) and `highlightSetPinnedId` (an optional re-centered member) in `GraphView.tsx`, threaded into `ForceGraph.tsx` as props, and mutually exclusive with `selectedId` (click-focus) by construction: setting one always clears the other. A set has no single "hero" node the way a click-focus cluster has the clicked artist, which is the source of almost every set-specific bug found so far:
- **Hub picking (`pickSetHub`) uses in-set degree, not graph-wide degree.** The spread/camera-fit code needs ONE representative node to anchor around (mirroring click-focus's own node). Picking by raw graph-wide degree chose hubs (Kraftwerk for krautrock, Cocteau Twins for dream-pop) with huge influence from OUTSIDE the set, leaving most real members visually disconnected from "the center." In-set degree (ties broken by graph-wide degree) fixed krautrock (Kraftwerk → Neu!, cutting disconnected members from 5/6 to 2/6) but couldn't fix dream-pop (still 13/22 disconnected from Cocteau Twins under either heuristic) — some sets genuinely have no single internal hub, several disjoint sub-clusters instead, and that's a property of the tag, not a bug.
- **Spread factor is a separate, smaller constant for sets** (`SET_SPREAD_FACTOR = 1.6` vs click-focus's `SPREAD_FACTOR = 2.6`). Proven via an offline `d3-force-3d` replica script that uniform-factor scaling from ANY origin point preserves the bounding box exactly — hub choice can fix jitter/pile-up but can NEVER shrink an over-zoomed-out frame; only the factor itself controls that.
- **Ghost dimming (background/non-member nodes) must follow the real cloud-zoom curve, not be forced to full-detail-size regardless of camera distance.** The relevant gate is `isInFocusCluster` (per-NODE: is *this* node the focused node/its neighbor/a set member) — NOT `isFocusModeActive`/`isNodeFocusActive` (per-MODE: is focus-or-set active AT ALL). Getting this backwards was the root cause of two separate bugs: dimmed background nodes rendering as a wall of full-size, merely-faded circles instead of shrinking to small cloud dots at a set's typically-lower camera zoom (fixed by keying `zoomFade`/`cloudDotFade`/`overviewSizeShrink` off `isInFocusCluster`), and the highlighted set MEMBERS themselves incorrectly inheriting the real (low) zoom curve too since the mode-level flag doesn't distinguish member from non-member (same fix, opposite direction: members now force full detail via the same `isInFocusCluster` check).
- **`SET_ZOOM_SIZE_REFERENCE = 1.3` is a second zoom-size-dampening threshold, separate from click-focus's `ZOOM_SIZE_REFERENCE = 3.5`.** The dampening effect (nodes shrink relative to spacing above the reference zoom — see Zoom-based cloud/detail reveal below) never engaged for sets at all when both modes shared one threshold: click-focus's tight clusters naturally sit right at/above 3.5, but a spread-out set rests around 1.0–1.6 and would need to zoom in far past its own comfortable viewing range to ever cross 3.5. Every place that calls `computeZoomSizeMult` now passes `isSetModeActive ? SET_ZOOM_SIZE_REFERENCE : ZOOM_SIZE_REFERENCE` explicitly (`drawNode`, `paintNodePointerArea`; label fontSize reuses the already-computed multiplier).
- **Hover-driven reveal (photo, neighbor highlighting, edge/arrow brightening) must check `isSetModeActive` in addition to `selectedId === null`.** Click-focus gets this suppression for free (`selectedId !== null` alone blocks it), but a set leaves `selectedId` null by design, so every `isHovered`/`isHoverNeighbor`/`isHoverEdge` check (`drawNode`, `paintNodePointerArea`, `drawLink`, `linkDirectionalArrowLength`/`RelPos`) and the `neighborSet`/`activeHighlightId` memo needed an explicit `!isSetModeActive` added — otherwise hovering any node outside an active set fully un-dimmed it and lit up its real, unrelated neighbors and edges.
- **Clicking a set member re-centers the set on that member (`onSetMemberClick` → `highlightSetPinnedId`) instead of exiting to full click-focus.** `getActiveCluster`'s hub selection prefers `highlightSetPinnedId` when it's a valid member of the current set, falling back to `pickSetHub` otherwise; clicking a non-member still exits to normal click-focus as before. The artist info panel's subject is `selectedId ?? highlightSetPinnedId`, so browsing within a set still shows bios; closing the panel unpins rather than exiting the set entirely (only clears `selectedId`-driven focus fully).
- **The cloud-dot sprite stamp (background/dimmed nodes' small colored point at cloud zoom) needed a visibility-floor early-exit** (`dotBrightness > 0.01`, mirroring the bloom-haze block's existing `alpha > 0.01` gate) once ghost dimming started actually running that code path for sets: with `autoPauseRedraw={false}` forcing a repaint every frame, ~270 background nodes all paying for two sprite stamps each, every frame, at a set's typically-low camera zoom (where click-focus's typically-high zoom made the block a no-op) was a real, measurable lag source — not present before ghost dimming was fixed to actually engage for sets.

**`/genres` is a subway-map-style timeline (`lib/genre-timeline.ts` layout + `components/genres/GenreTimeline.tsx` render), positioning every dated genre by when it emerged and by lineage.** Pure layout math lives in the lib file (server-safe, resolves final pixel x/y so the component doesn't redo it), rendering/hover/click lives in the component.
- **X-axis is ordinal rank among dated genres, not a linear year scale** — sorted by `(emerged, name)`, evenly spaced by count. A dense period (1978–85, 11 genres) gets 11 columns of width; a sparse one (1963–76, 5 genres) gets 5 — deliberately NOT proportional to elapsed calendar time, which would bury the dense period in a sliver.
- **Y-lanes use heavy-path decomposition + greedy interval-graph coloring, not one permanent row per branch.** Within a band, the highest-count child continues the parent's lane (the "trunk"); every other child starts a new chain. Chains are then packed into physical rows greedily — a chain's row can be reused by a later, unrelated chain once the first one's occupied x-range has ended, so a single-node band costs exactly one row instead of reserving a row per branch forever.
- **The graph's 15 real top-level genres (10 true `parent: null` roots + 5 `folk`-orphans, since `folk` is an invisible container) are NOT force-fit into "six lineages."** A curated 6-hue color-family palette (`BAND_FAMILY` in the lib file) groups them for legibility, but every drawn line is still a real `parent` pointer — no edge is invented between same-family bands that aren't actually connected (e.g. garage-rock and art-rock share a gold hue with no line between them).
- **9 tiny orphan bands (zero or one child each — see the childless-roots list in Data model, plus power-pop's 2-node band) are collapsed into one shared "compact strip" at the bottom** rather than each keeping its own dedicated lane + band gap — this alone freed most of the vertical room now spent on the 6 real bands (see next point). The compact strip's own row count is NOT hardcoded — it's computed via the same interval-coloring, but with each chain's occupied interval extended by its own label's estimated pixel width (converted to rank-units), not just its bare x-position: two dots can be far enough apart to never visually touch (e.g. garage-rock 1963 / minimalism 1964, one rank apart) while their *labels* would still collide, and label-aware packing is what correctly puts them on separate rows.
- **Major-band lane pitch scales with how many lanes that band needs** (`BASE_LANE_PITCH + EXTRA_PITCH_PER_LANE × (laneCount − 1)`) instead of one fixed pitch everywhere — a band with 5 branches (proto-punk) gets noticeably more vertical room per lane than a 1-lane band (art-rock), funded by the space the compact-strip collapse freed up.
- **Only band roots + genres above a `count` threshold get a permanent label; everything else is dot-only until hovered.** Hovering any node highlights its full ancestor chain (via `parentId`) up to its band root and reveals labels for every node in that chain, dimming everything else — this is the mechanism that makes the ~20 non-landmark genres legible at all, not a decoration.
- **Every visible label gets a solid background chip**, not a repositioned line — a diagonal branch line from an unrelated node can cross behind any label regardless of where it's placed, so a chip (same pattern the main graph canvas already uses for its own labels) is the only fix that's unconditional rather than case-by-case.
- **The hover tooltip is an HTML element positioned via `e.clientX/clientY`, deliberately OUTSIDE the SVG's `viewBox`-scaled coordinate space.** The diagram's own inline labels are SVG text that shrinks proportionally with the whole `viewBox` at narrower viewports (a real, unresolved tradeoff — see Pending below); the tooltip stays at real, full CSS-pixel size regardless, so a genre is always fully identifiable via hover even when its inline label has become too small to read.
- **This page briefly imported `data/seed-data.ts`'s raw `graphData` directly instead of `loadGraphData()`**, because the genre metadata pass had only been written to `seed-data.ts` (not yet baked into `public/graph.json` — `build:data` was deliberately withheld for that pass). Switched back to the normal `loadGraphData()` pattern once `build:data` was actually run and `public/graph.json` picked up the fix — if you ever see raw `seed-data.ts` imported from a page again, that's a sign `build:data` needs to run before removing the workaround, not a pattern to copy elsewhere.

## Data model

`data/seed-data.ts` → `data/types.ts` for full interface definitions.

**Artist**
```
id           slug, kebab-case, stable forever
name         display name
layer        'root' | 'post-punk' | 'shoegaze-dreampop' | 'indie-alt' | 'outside'
realm        'core' | 'region-one' | 'electronic' | 'folk-confessional' | 'emo-posthardcore' | 'post-rock-drone-noise' | 'american-underground' — orthogonal to layer, drives graph clustering + resolver color fallback (see Realm/lineage color model above)
lineage      sub-family within a non-core, non-region-one realm — electronic: krautrock/synth-pop/idm/ambient-drone/electronic-indie-dancepunk/trip-hop-downtempo/hyperpop-pcmusic/art-electronic · folk-confessional: folk-roots/freak-folk/confessional/slowcore/indie-folk · emo-posthardcore: hardcore-roots/post-hardcore/midwest-emo/math-rock · post-rock-drone-noise: post-rock/no-wave/drone · american-underground: noise-alt/college-rock/indie-rock/psych/neo-psych. Only set when realm is one of these five.
scope        array of scope tags (e.g. ['shoegaze-dreampop-v1', 'indie'])
genres       array of genre IDs (see genres list in seed-data)
country      ISO 2-letter
activeFrom   year (number)
bio          for the original 106 v1 artists: injected from data/bios.ts at build time (`BIOS[a.id] ?? a.bio`). Every realm added since electronic (folk-confessional onward) writes `bio` directly inline on the artist literal instead — `data/bios.ts` is not touched for new realms, and isn't the source of truth for most of the graph anymore.
imageUrl     artist photo — enriched at build time, null = placeholder
classicAlbums  array of Album (usually exactly 1)
```

**Album**
```
id           slug
title        display title
year         number
isClassic    true
classicReason  3–4 sentence write-up (see style below)
imageUrl     album cover — fetched from iTunes at build time, null = placeholder
spotifyId    optional, for SpotifyEmbed
```

**Edge**
```
source / target   artist IDs (source = influenced BY target)
type              'influence'
status            'verified' | 'ai-suggested'
confidence        0–1
citation          source + what was said — a finished sentence for an end reader, not research notes (see rule below)
citationStatus    'unsourceable' | 'unchecked' | undefined — see resolveCitationStatus() in data/types.ts; 'cited' is derived from citation, never stored
sourceTier        'first-person' | 'reported' | 'critic' | undefined — who's speaking in citation; only meaningful alongside a real citation
```

**Citation discipline (folk/emo/post-rock/american-underground on):** every edge added since the folk-confessional realm carries a real, named, checkable source in `citation` — never left null, never invented. `confidence` is used as a sourcing-tier signal on these newer edges, not just a vague "how sure are we": ~0.85 for a first-person artist quote, ~0.6–0.7 for a critic claim corroborated across independent sources, ~0.5 for a single-source critic comparison or an explicitly flagged weak/thin source.

**`citation` text must read as a finished sentence for an end reader, never as research notes.** This is a hard rule, added after a citation-UI pass found ~430 of 522 cited edges leaking internal vocabulary into reader-facing text. Specifically, never put any of the following inside a `citation` string:
- **A confidence/sourcing tier** (`HIGH --`, `MEDIUM, critic --`, `WEAK`, `single-source`, etc.). That's what `sourceTier` is for — a structured field a UI can render as a marker, not a word for the reader to parse out of prose. Set `sourceTier` from the same judgment that used to produce the tier tag: `'first-person'` for a direct/reported artist quote, `'reported'` for a publication stating/listing the fact with no quote, `'critic'` for a critic's comparison or analysis.
- **A reference to this repo** (`scripts/output/influence-audit.md`, `*-audit-DRAFT.md`, a node id like `x -> y`) or to another edge's citation (`"same quote as fugazi -> bad-brains"`). If two edges share one source, put the actual source (publication, who, year, what was said, trimmed short) on each edge independently — repeating a short line honestly reflects that one interview sourced several edges; a cross-reference by id does not belong in reader-facing text.
- **An apology about the sourcing pipeline** (`"specific quoted wording not preserved there"`, `"not independently re-fetched"`). If the source is thin, say what it actually is (`"Wikipedia's X page"`) rather than explaining why it's thin.

**Grokipedia is an AI-generated wiki and must never be used as a source.** It ranks in search results, presents claims with footnote-style numbers that look like real citations, and fabricates influence claims. Two confirmed instances (region-one research pass): an invented "Camera Obscura grew up on the Velvet Underground, the Pastels and Yo La Tengo" claim traceable to no real interview, and an unverifiable Stereolab influence claim. It is more dangerous than TV Tropes because it *looks* sourced. If it appears in search results, discard it and note the discard rather than silently omitting it. Confirmed working: it surfaced and was discarded four more times in the electronic research pass (Magdalena Bay, Lamp, Mid-Air Thief, Grouper) with no bad citation slipping through.

**Mechanically-recycled bio blurbs on aggregator sites are not citations either, even when several sites repeat the identical wording.** Found in the electronic realm's honeydip research: a specific, identically-worded claim ("primarily influenced by the artists from the 4AD label such as Bauhaus, Cocteau Twins, Lush, and Pale Saints") recurs across Last.fm and RateYourMusic-adjacent bios, traces to no named interview, article, or even an English Wikipedia page, and reads as a copied blurb propagating between sites rather than independent reporting. Two of the four named artists (Cocteau Twins, Lush) are graph nodes, so this offered two plausible in-graph edges sitting on top of a single unverifiable claim. **Repetition across aggregators is not corroboration** — if several sources use identical or near-identical wording and none names an origin, treat it as one unsourced claim, not many independently-corroborating ones.

`citationStatus: 'unsourceable'` is the correct place for "this is real and undisputed but no artist has stated it on the record" — that is a finding, not a hedge, and belongs on the edge as structured state, not woven into `citation` prose.

**RejectedEdge** (on `GraphData.rejectedEdges`, separate array from `edges`)
```
source     the artist who denies it
target     the claimed influence
citation   source + what was actually said
strength   'clean' | 'contested'
```
Recorded artist denials of a commonly-assumed influence (e.g. Car Seat Headrest explicitly denying Pavement/Sonic Youth/Dinosaur Jr./the Strokes), so a future research pass doesn't re-propose and "confirm" the same false edge off the same critic comparisons. **30 entries** as of this writing (check `graphData.rejectedEdges.length` directly rather than trusting this number) — 15 documented as of the region-one/final-roster passes (the original 9 from the american-underground realm's research, see `realm6-audit-DRAFT.md` §6/§10, plus 4 from the region-one extension: Interpol/Chameleons, Chameleons/Joy Division, Cranberries/Sundays, Radio Dept./JAMC, plus 2 from the final roster additions: Perfume Genius/Talk Talk, Songs: Ohia/Leonard Cohen), and 7 more added since — likely from the directional edge pass (31 Jul 2026, which explicitly logged denials alongside its ~49 new edges) but not individually re-verified against that pass's notes; confirm the specific 7 before citing them by name. **Not surfaced in the artist panel's Influences list** — a denial isn't an influence, and putting one next to a list of things the artist *was* shaped by inverts the list's meaning. If/when a UI is built for these, it needs its own clearly-labeled section, shown only where `rejectedEdges` has entries for that artist (the large majority of artists have none).

**Genre** (on `GraphData.genres`, the `id`s referenced by every artist's `genres[]`)
```
id             slug, kebab-case
name           display name
parent         parent genre id, or null for a root — see the hierarchy rule below
emerged        year the genre emerged — undefined for pure containers (electronic, folk, indie, underground)
emergedBasis   what that year refers to — an album, a term being coined, a scene forming
```
**`emergedBasis` is not optional in practice, same discipline as edge `citation`.** Emergence dates are genuinely contested (post-rock is 1991 or 1994 depending whether you date it from *Laughing Stock* or from Simon Reynolds coining the term) — a bare year is an unsupportable claim, a year plus a named reference is a defensible position. 51 of 55 genres carry a year; `electronic`, `folk`, `indie`, `underground` deliberately don't (they're containers, not points on a timeline).

**`parent` must express genuine musical descent, not bucketing.** This was audited and fixed across two passes (2026). **Pass 1** removed `indie`/`underground` bucketing: every genre pointing at either purely as an organizational bucket (rather than a real ancestor) was re-parented to its actual lineage (e.g. `shoegaze → dream-pop`, `noise-rock → no-wave`, `punk → proto-punk`) or promoted to root (e.g. `art-rock`, `krautrock`, `indie-rock`, `alt-rock`), and several chronologically-backwards parents were corrected (`garage-rock → alt-rock` was off by 25 years). That pass left `indie-pop → indie-rock` broken (indie-pop 1983 predating indie-rock 1990 by 7 years) and `krautrock` a childless root despite being the real ancestor of everything under the `electronic` container. **Pass 2** fixed both: `indie-pop → post-punk` (same reasoning as jangle-pop's fix), and the entire electronic fan reparented off the `electronic` container onto `krautrock` — `synth-pop`/`ambient`/`industrial → krautrock` directly, then `idm → synth-pop`, `hyperpop → idm`, `drone`/`trip-hop → ambient`, plus `vaporwave → hypnagogic-pop` (extending the psychedelic-pop branch) and `jangle-pop → power-pop` (rescuing power-pop from being childless). `electronic → underground`, `folk → underground`, `indie → underground` remain the deliberate structural container chain — those three are containers pointing at containers, which is fine; the bug was real genres pointing at containers as if a container were an ancestor, and `electronic` itself is now a true leaf container (zero children of its own) since everything under it moved to a real lineage. **Remaining childless roots, confirmed as genuinely having no better fit in the vocabulary, not an oversight:** `garage-rock`, `minimalism`, `post-rock`. `Genre.parent`/`emerged` now power `/genres` (see Architecture decisions and Current state below) — no longer unread prep.

**classicReason style:** 3–4 tight, punchy sentences. One sharp point about sound, one about a standout track or technical detail, why it endures. No mini-essays. Straight ASCII double-quote delimiters only.

Current, settled design of `/scenes` (`app/(graph)/scenes/page.tsx`, `lib/scenes-timeline.ts`, `components/scenes/ScenesTimeline.tsx`):
  - **One row per scene — packed, shared rows were tried and reverted.** A greedy interval-graph-coloring pack (same technique `/genres` uses for its own lane packing) let non-overlapping scenes share a horizontal line and got 12 scenes down to 8 rows. It broke hover: two scenes in the same row means two full-width row `<div>`s stacked at the identical top/height, and the later one in DOM order silently intercepts pointer events across its ENTIRE width — including wherever the OTHER scene's bar sits — even though it has no visible content there. Reverted to one row per scene (`resolveSceneTimelineScenes` in `lib/scenes-timeline.ts`), which guarantees no two rows ever share a vertical position. The page is taller for it (12 rows, no longer trying to fit one screen — see below) and that's the intended tradeoff: taking up more of the page is fine, a bar you can't hover isn't.
  - **An open-ended scene's synthetic `yearEnd` is the CURRENT year, not `yearStart + 4`.** `resolveOpenEndedYearEnd` derives it (`Math.max(yearStart + OPEN_ENDED_MIN_SPAN, currentYear)`), so an ongoing scene's bar reaches the present and grows on its own. The old flat +4 silently went stale: by 2026 it drew Windmill — running since 2016 — as a 58px sliver against the 136px it should have, pinned to the right edge and reported as looking cut off. Because `axisEnd` is `max(yearEnd)`, this also moves the axis end (now 1961–2026), which the `/scenes` deck picks up automatically since it derives its range. The `OPEN_ENDED_MIN_SPAN` floor remains so a scene starting this year can't collapse to zero width. Note this makes the axis end build-time dependent — the value is resolved server-side in `resolveSceneTimelineScenes` and passed to the client component, so there is no hydration mismatch, but a stale build will show a stale end year.
  - **An open-ended bar's gradient must never reach full transparency.** It tapers to ~42% alpha at 100%, not to `transparent`. Fading to nothing meant the last chunk of the bar was invisible, so a scene that does run to the axis edge read as stopping short of it — reported as the bar being "cut off before the end." The taper still has to be there (it is what distinguishes ongoing from ended, alongside the squared-off right corner); it just has to still be ink at the extreme edge.
  - **The hover tooltip flips above the bar for rows near the bottom (`flipTooltipUp`), and that is a scroll fix, not a cosmetic one.** `.scenes-overlay` is the page's scroll container, so a tooltip hanging past the plot's bottom edge grew its scrollable height on hover and shrank it again on unhover — the page visibly jumped every time the pointer left a bottom-row bar. When flipped it anchors by `bottom` (`plotHeight - rowTop + 6`) so it grows upward from the bar's top edge and never needs its own height measured. The decision uses `TOOLTIP_RESERVE_PX` (132), a deliberate over-estimate rather than a measurement — measuring would mean rendering then repositioning, which flickers on first hover, and erring large only flips a row early. At a 562px plot the bottom four rows flip; at 460px, five.
  - **The time axis is non-linear (density-weighted), not a year scale.** `computeAxis` returns an `AxisScale` with a `yearToPct(year)` mapping instead of a bare `span`; every bar edge and every tick goes through it. Built by cutting the axis at every `yearStart`/`yearEnd`, counting how many scenes overlap each segment, and giving the segment width proportional to `duration * (DENSITY_FLOOR + sceneCount)`, with linear interpolation inside a segment so the mapping stays continuous and strictly increasing. Same principle as `/genres` (ordinal rank rather than calendar time) but it could not be borrowed directly: a genre is a point, a scene is an interval, so this needs a continuous year→position function both ends of a bar can go through. **Effect at 14 scenes: 1976–2000 went from 40.7% of the width (linear) to 69.6%**, and the two dead stretches (1965–68, 2010–16) collapsed from ~15%/~10% to under 2% each. `DENSITY_FLOOR = 0.35` is what an empty year is worth against a year holding one scene — raise to flatten, lower to compress the margins harder. **Consequence worth knowing: bar width no longer maps linearly to duration.** SST (12 years, dense) draws wider than Glasgow (14 years, sparse), which is intended — width is span *on the weighted axis*.
  - **Year ticks stay on the every-5-years grid and are deliberately NOT re-spaced.** Uneven tick gaps are the honest readout of the non-linear axis; evenly spaced ones would hide exactly the compression being applied. A tick is dropped only when it would land within `MIN_TICK_GAP_PX` (34) of the previously kept one or of the right edge, since two overlapping four-digit labels are worse than one absent one — 2015 is currently the only casualty (19px from 2010). Both endpoints always survive.
  - **The dashed "true end" tick and the bar-extension mechanism behind it are gone.** A bar's width is now always its true span. Bars used to be allowed to grow past their real end year when member faces would not otherwise fit, with a dashed mark admitting the distortion (CBGB, 3 years and 4 members, was the case it existed for) — that traded a correct chart for a footnote explaining an incorrect one, and read as a rendering glitch. Faces now shrink per bar instead: `computeBarGeometry` returns its own `faceSize`/`faceStep`, capped at the global values from `computeVerticalSizing` and floored at `MIN_BAR_FACE_SIZE` (11). Only CBGB (13px) and Windmill (15px) shrink at all against a 17px global. **Note the rounding trap:** the fitted size is solved in floats but `faceStep` is rounded, and rounding up can push a row back over the width it was just solved for — there is a step-down loop for exactly that, and removing it reintroduces a one-pixel overflow on the two bars this logic protects. Also note `.scenes-timeline__faces { left: 14px }` in globals.css owns the strip's left inset (mirrored as `FACES_LEFT_INSET_PX`); `computeVerticalSizing`'s `facePad` is a different number and is not used by the renderer at all.
  - ~~**Row order is by member count descending, not by start year**~~ — **REVERSED at 14 scenes; rows now sort by `yearStart` ascending, member count descending as tiebreak.** The old reasoning (start-year order makes a diagonal staircase with empty triangles, count order scatters early/late bars so the composition doesn't read as a ramp) held at 12 scenes inside a 44-year window, where bars clustered horizontally anyway and the scatter was invisible. It stopped holding once the axis stretched to 59 years (1961-2020) with three scenes isolated in the sparse left third: row position became unrelated to bar position, reading down the rows gave 28.8% -> 32.2% -> ... -> 93.2% -> 11.9% -> ..., and the earliest scene of all (Greenwich Village, left edge 0%) sat at row 12 with twelve rows of empty space above and left of it. Measured deviation between row order and chronological order was **3.57 rows mean, 12 max**, reported directly as the page looking disjointed with one bar "lonely in a corner." Sorted by year, the staircase is back and its empty triangles are just the shape of the data; what it buys is that the two isolated bars become the timeline's endpoints instead of outliers, and chronology becomes scannable top-to-bottom. The shared time axis (unaffected by row order either way) still shows every real overlap (SST/DC Hardcore, Bristol/Seattle, riot grrrl/Seattle). **Don't re-revert this from the older note — the trade flipped because the data changed, not because the earlier reasoning was wrong.**

## Discipline / hard rules

These aren't aspirational — they're the pattern the codebase itself was built with (see the `island-two` electronic-lineage merge: sandboxed at `data/island-two-data.ts` → tuned in isolation at `/lab/merged` → merged into the real graph → lab scaffolding deleted, each as its own commit).

- **Read the current code before changing anything.** Don't assume this doc, or your last session, still matches what's in the files — verify against `data/seed-data.ts`, `lib/colors.ts`, `data/types.ts`, and the component you're touching first. In particular: before writing any new node or edge, check whether the id already exists (it may already be a fully-developed node in a different realm — see the Stereolab case in the american-underground work, where the artist was already a region-one node and was correctly left alone rather than duplicated or moved).
- **Edit region-one data and shared components additively and backward-compatibly.** New realms/lineages/features must extend, not alter, existing behavior for real region-one artists. The concrete mechanism for this is the `!node.realm` fallback branch in every `resolve*` function in `lib/colors.ts` — any new color/label axis must preserve that branch untouched.
- **One change at a time.** Land a sandboxed/isolated version first (a new file, a `/lab` route, an additive field), confirm it doesn't touch existing rendering, then merge — don't do the merge and the new feature in the same step.
- **Never write scripts to surgically edit `seed-data.ts`** — see the quirk below.
- **New realm data goes through three layers, not straight to code.** Established across folk-confessional, emo-posthardcore, post-rock-drone-noise, and american-underground: **Layer 1** is pure research (an `*-audit-DRAFT.md` file at the repo root — per-artist real, named, checkable sources for who influenced whom, explicitly researching each artist's actual documented influence network rather than validating a fixed pre-guessed pair list, which is what caused the folk realm's first pass to under-count). **Layer 2** is the reviewer applying rulings on top of that research (confidence tiers, summon/cut/hold decisions, denial tracking, chronology checks) without re-researching. **Layer 3** is the actual write to `seed-data.ts`/`types.ts`/`lib/colors.ts`/`ForceGraph.tsx` — structure and edges first (no bios/albums), content (bios/classicReason) as a separate later pass. Never skip a layer or collapse research and writing into the same step.
- **Verified edges only; never invent a citation.** If a real, specific, checkable source can't be found for a claimed influence, mark it UNSOURCED/drop it — do not write a plausible-sounding but unverified claim, and do not invent quote text to fill a citation string. If a needed source file is genuinely unavailable (this happened once, with `realm6-handoff.md`), hold the affected nodes/edges rather than guess, and say so explicitly when reporting back.
- **A node with zero real edges is held, not written ("no orphans").** Established with `the-apples-in-stereo` and `broken-social-scene` (emo/american-underground research found their entire relationship sets were personnel/production/label/simultaneity, not influence), and again with Panda Bear. Writing a 0-edge node just to match a roster count is worse than leaving it out and saying why.
- **Personnel overlap, production credit, shared label, and collaboration are not influence edges.** A recurring false-positive category across every realm audit — a member also being in another band, a producer/engineer relationship (e.g. Dave Fridmann producing both the Flaming Lips and Tame Impala/MGMT), a shared record label, or a guest feature all *look* like a citable connection and are not one. Check for this specifically before writing an edge that seems too easy.
- **No Playwright/browser-launch verification unless explicitly requested.** Verify CSS/layout changes by reading the code and the rendered HTML — `curl` against the dev server is fine for confirming a route responds or a class/string is present. Where a change is purely visual (colors, spacing, whether something "looks right"), say it's done and let the user look themselves. A browser launch per check costs far more than the check is worth — this was called out directly after a session that used Playwright screenshots to verify a run of CSS-only fixes.

### Search method (added after the directional edge pass, 31 Jul 2026 — 64 edges found across 5 passes/~50 searches)

- **Never search "who cites X." Search the suspected descendant's own interviews.** Confirmed nine separate times: every per-descendant search (Fiona Apple, Bon Iver, Jeff Buckley, Hum, Snail Mail, Waxahatchee, Japanese Breakfast, and others) produced first-person material on the first try. Every root-outward "who was influenced by X" search produced critic resemblance or nothing. Not one of the 64 edges found in that pass came from a query containing the word "influence."
- **Upstream is cheap; downstream is expensive.** Upstream (an artist's own stated influences) averaged one search per 2–5 edges. Downstream (who a given artist influenced) averaged 1–2 searches per 0–2 edges. The question has a bounded answer only one direction round — budget research time accordingly, and don't be surprised when a node's true downstream count is genuinely low.
- **Three source formats carry almost everything:** The Quietus's *Baker's Dozen* franchise, gear-and-technique interviews (an artist discussing a specific pedal, tuning, or recording setup tends to name real influences as a side effect), and book-length interviews/biographies.
- **Anchor searches to album titles, not artist names, when the artist's name is a common word — and this isn't only useful for common-word names.** Roster artists like Beck, Wire, Hum, Low, Women, Suicide, Sparks, Faust, and Codeine won't resolve on the name alone — Beck collides with Jeff Beck and JD Beck, for instance. But it also resolved Snail Mail and Low after ordinary artist-name queries had already failed on both, so try it even when the name isn't ambiguous.
- **Chronology: test release dates, not formation dates.** Two edges in the folk-confessional verification pass (`phoebe-bridgers → big-thief`, `phoebe-bridgers → mitski`) were wrongly flagged as chronologically impossible on the artists' formation dates and turned out valid once checked against release dates instead (Big Thief's *Masterpiece* 2016, Mitski's *Lush* 2012, Bridgers' *Stranger in the Alps* 2017). When the influence concerns a specific recorded work, the record's release date is the test — a younger band can still release before an older one's defining record does.
- **Artist-authored playlist commentary is admissible; editorially-curated playlists are not.** The existing Apple Music "Influences" exclusion is about commentary the *publication* writes around an artefact — but Clairo took over her own Apple Music playlist and wrote per-song notes herself, which is a favourites list in a playlist wrapper, not the excluded thing. Rule: exclude editorially-curated influence playlists; accept artist-authored playlist commentary at favourites tier.
- **Documented repertoire reaches reported tier for artists who left no interviews.** How `nick-drake → bob-dylan` resolved — Drake recorded "Tomorrow Is a Long Time" at home, and that recorded fact carries the edge in the absence of any interview to quote.
- **Don't infer `unsourceable` from one interview's silence.** One negative search isn't evidence of absence — an edge marked `unsourceable` after a single fruitless search should be treated as unverified, not settled, since a second attempt in the folk-confessional pass overturned exactly this kind of premature call.
- **A verified-low edge count is a real answer, not an unfinished search.** For several nodes across this project (Bob Dylan upstream, LCD Soundsystem downstream, Hum downstream, Pinback downstream, Olivia Tremor Control, Duster downstream, Nico downstream — see `directional-edge-pass-CONSOLIDATED.md` §5) a thin or zero count survived a real, careful search and is the honest answer against a closed roster, not a gap waiting for the next pass to fill. Re-running a settled node wastes the next pass's search budget. A `researchStatus`-style field to mark a node as settled-not-unchecked was proposed but not yet implemented — see the same file's §6a for the shape.
- **Some nodes generate more false edges than real ones simply from adjacency** — sitting inside a label roster, a scene, or a producer's orbit (LCD Soundsystem: production + personnel + DFA label + 2002 simultaneity, all four at once; Olivia Tremor Control: Elephant 6 personnel; Superchunk: Merge; Sleater-Kinney: riot grrrl + Kill Rock Stars + predecessor-band personnel; Pinback: six side projects). Check personnel/label/scene/simultaneity *first* on any proposed edge touching these nodes specifically. A hazard-flag field was proposed but not yet implemented — see `directional-edge-pass-CONSOLIDATED.md` §6b.
- **Grokipedia's failure mode is substitution, not invention — this is worse than open fabrication, because the substituted name is always credible.** Now at 13+ encounters, 4 confirmed errors (the fourth, Aug 2026: it was the origin of an unsourced "drawing on influences like Elliott Smith and Conor Oberst" claim about Dev Hynes, both of which would have been roster edges): it invented The Clash as a Bad Brains influence (every real first-person account instead names Sex Pistols, Ramones, Dead Boys, Generation X, and The Damned); it claimed the 2008 Fleet Foxes album influenced Bon Iver's 2007 debut, a hard chronological impossibility; and in the folk-confessional pass it invented Mac DeMarco's Neil Young records as coming from his parents' collection, when DeMarco has said in interviews they came from a thrift-store dollar bin. All three pointed at real graph artists and all three would have produced encodable-looking edges if not checked against other sources.
- **Critic "you can hear X in Y" sentences do not check dates.** One Stereogum sentence named five graph artists as Olivia Tremor Control descendants; three of the five were chronologically impossible (formed before OTC). Six chronological impossibilities were caught across the directional edge pass alone, always from the same kind of source: a critic asserting a resemblance-based lineage without checking formation dates. Always check chronology before writing an edge sourced to this kind of sentence.
- **The AllMusic panel-vs-prose distinction keeps earning its keep.** AllMusic's prose biography has produced nine usable edges across two passes; AllMusic's influences-panel widget has produced zero usable edges and multiple tempting false positives from the exact same domain (Liz Phair's panel alone offered 16 names, all four of her real targets among them, none citable). The distinction is claim vs. bare name, not source size or prestige — keep enforcing both halves of the existing rule.
- **Block The Student Playlist's "Influenced by:" lists at source level, not case by case.** Encountered twice now; the worst instance held 19 graph artists across two unsourced lists, two of which failed chronology outright. This is the single largest false-positive cache found across two passes — treat any "Influenced by:" header list from this site as excluded on sight, not worth even a second look.
- **The search tool itself can fabricate a quote, and this defeats every source-level rule in this file.** Found in the final unchecked-edges pass (Aug 2026): a WebSearch result summary asserted that Matt Pryor said *"My guitar is attempting to channel Drive Like Jehu"* in an Alternative Press track-by-track. It cited no URL; the exact phrase returns zero results; no such feature exists; none of the returned links contained it. This is Grokipedia's substitution failure mode (a credible, specific, immediately-encodable claim with no origin) arriving one layer earlier — **the Grokipedia rule cannot catch it, because there is no bad domain to discard.** The only defence is to treat a quote that appears in a search *summary* rather than in a page you actually read as unverified until the exact phrase is searched and a real source is opened. Do that for every quote before it becomes a `citation` string.

- **`r.jina.ai/<url>` defeats most publisher 403s, and doubles as a search engine when the WebSearch budget is gone.** Found in the R&B pass (Aug 2026) after four separate holds across this project traced to the same blocks. It recovered full pages from The Quietus and Interview Magazine that had 403'd on every direct attempt across three prior passes — including the Tyler Hyde Baker's Dozen that had cost three edges. `r.jina.ai/https://duckduckgo.com/html/?q=…` also works as a substitute search once WebSearch is exhausted. It is not universal: `thecut.com` refuses it too, and `web.archive.org` is blocked to the fetch tool outright. Try it **before** recording a hold for an unreachable source.
- **The WebSearch cap is 200 calls, session-wide, shared across every subagent.** Measured directly in the R&B pass, which hit 200/200 mid-run with three agents sharing one pool. This is the concrete number behind the warning below: parallel agents do not get parallel budgets, they divide one. Sequence research passes, and have each agent report its own tool status so a thin result can be told from a blocked one — both agents did, which is what made the Kelela gap identifiable as *unfinished* rather than *empty*.
- **A search summary can be accurate in substance and wrong in attribution — a subtler variant of the fabricated-quote failure.** The Alex G / Frank Ocean summary asserted a real influence statement and returned the Vice and Stereogum interviews alongside it. The statement is genuine, but it appears in **neither** of those pieces; the actual quote lives in a third publication (Time Out New York). Had the citation been written from the summary it would have named a source that does not carry the quote — checkable-looking, and wrong. Always locate the page that actually carries the sentence, not merely a page the summary returned next to it.
- **Watch for name collisions that poison a search.** Snail Mail's stated influences include the poet **Frank O'Hara**, which contaminates any "Snail Mail Frank Ocean" query. Same class as the Beck/Wire/Hum/Low ambiguity already documented — anchor to album titles when a search keeps returning the wrong entity.

### New traps found in the folk-confessional verification pass (31 Jul 2026)

- **Whose "I" is it.** A Noisey piece on John Darnielle contains the *journalist's* own teenage listening list, not Darnielle's — six graph artists misattributable, and only the following paragraph reveals whose history is actually being described. Always confirm whose account a first-person-sounding passage belongs to before citing it as the artist's own.
- **Page collisions.** An Audiofemme page tagged for Mitski turned out to carry a Liz Phair sentence actually about Frankie Cosmos; an LSQ page about Robin Pecknold had Justin Vernon's Eau Claire/Discman origin story bleeding in from an adjacent section. Read the surrounding paragraphs, not just the sentence a search result highlights.
- **Critic claims derived from label rosters.** Drowned In Sound inferred Red House Painters' influences from 4AD's catalogue — it reads as a normal prose claim, passing the panel-vs-prose test on the surface, but the actual reasoning underneath is label adjacency, the same non-influence category the personnel/production/label rule already excludes. Check what a claim's *reasoning* actually rests on, not just its surface format.
- **Covers albums generate false edges more readily than single covers, because a whole album looks like devotion.** This is exactly how `red-house-painters → modest-mouse` was born — Mark Kozelek's Sun Kil Moon covers album of Modest Mouse songs (*Tiny Cities*, 2005) got misread as an influence claim, with both the direction and the chronology wrong (Red House Painters formed in 1988, Modest Mouse in 1992).
- **"X by Y" interview formats can name the wrong person as the subject.** BOMB's "Joanna Newsom by Roy Harper" is Harper *interviewing* Newsom, not the reverse — Harper is the interviewer, not a subject expressing influence.
- **Solo-vs-band timeframe matters for classic-rock-era artists especially.** John Cale's *Fear* (1974) and Lou Reed's *The Bells* (1979) are solo records, years after the Velvet Underground disbanded — citing either does not resolve a Velvet Underground edge, even though both artists were VU members.

### Two structural findings

- **Discovery and verification are not separable exercises — run them together on the same realm.** Nico's downstream defeated four separate dedicated discovery passes and was recommended as settled at in-degree 4. Verifying a *different* realm (folk-confessional) turned up `elliott-smith → nico` at 0.85, incidentally, while checking something else entirely. A future pass should combine discovery and verification on the same realm in the same session rather than running them as separate exercises against different budgets.
- **A "definitive" handover document can still drop per-edge sourcing during consolidation.** The folk-confessional handover's CITED section listed 51 edges as sourced, but roughly three-quarters of them (everything outside the top confidence band) were compressed into bare `source → target` pairs with a confidence number and no actual quote or named publication — an information-loss artifact of summarizing six prior working files into one. Only the edges that still carried real, specific source text got written; the rest were left `unchecked` and flagged rather than guessed at. When consolidating research notes into a handover, keep the per-edge source text even when it feels repetitive — the summary table is not a substitute for it.

### New traps found in the unchecked-edges disposition pass (31 Jul 2026 — 105 unchecked edges disposed, ~110 new edges written)

- **Check for an artist-curated source before searching press.** Every best source in this pass was artist-curated: Nick Cave's Red Hand Files, cocteautwins.com, Björk's own site, Clairo's Apple Music takeover, Oklou's NTS mix, Ride's and Slowdive's dedicated Under the Radar influences interviews. Ranked, track-specific, no journalist standing between the artist and the claim.
- **A low in-degree usually means nobody searched the right descendants, not that there's nothing there.** Sufjan Stevens finished the folk-confessional pass at in-degree zero; this pass found two first-person incoming edges — from underscores and Parannoul — artists nobody would have thought to check for a connection to him.
- **Legacy confidence was set by apparent obviousness, not by evidence — assume the ~795 previously-cited edges may be similarly miscalibrated.** `dinosaur-jr → the-birthday-party` sat at 0.5 despite Lou Barlow saying outright "we were into The Birthday Party" and Mascis breaking eggs into his hair to copy Nick Cave's haircut; `cat-power → sonic-youth` sat at 0.8 with nothing behind it but a shared session drummer (since deleted, see `rejectedEdges`). Not worth a dedicated pass to fix on its own, but worth checking whenever an old edge's confidence looks off against a newly-found source.
- **In five of six denial cases resolved in this pass, the denied edge was that band's single most-repeated critical comparison** (Interpol/Joy Division, Television/Velvet Underground, Yeah Yeah Yeahs/Siouxsie). The obvious comparison is disproportionately the one artists reject on the record — treat a denial search as *more* worth doing, not less, precisely when a comparison is the one everybody already assumes.
- **"We don't sound like X" denies resemblance, not influence — don't delete on that quote alone.** `lush → my-bloody-valentine` was flagged for deletion on Anderson's "We don't sound like Ride. Or My Bloody Valentine," but a band can be genuinely shaped by something and still sound nothing like it. Downgraded and caveated instead of deleted.
- **A Sonemic *interview* is citable; Sonemic and RYM *user lists* are not** — the same claim-vs-bare-name split as the existing AllMusic panel-vs-prose rule. Sweet Trip's own influences (Slowdive, Sonic Youth, Aphex Twin) came from a real Sonemic interview with the band, not a user-submitted list.
- **Director-mediated influence: check whose influence it actually was when a node is a vocalist rather than an author.** `julee-cruise → cocteau-twins` looked like a normal artist-influence edge, but the Cocteau Twins influence on *Floating into the Night* belongs to David Lynch and Angelo Badalamenti — who wrote, composed, produced the record, and directed Cruise's vocal style — not to Cruise herself, who didn't write or produce it. Deleted rather than kept at a lower confidence, since the influence is real but doesn't attach to this node.
- **Cover-derived "influence" is a false-positive category, same shape as the Apple Music playlist rule.** A cover version, or a whole covers album, reads as devotion but isn't itself an influence claim — `big-thief → townes-van-zandt` and `jeff-buckley → leonard-cohen` were both rejected on exactly this pattern (a single-song cover for a themed series called *The Influences* is the series' own framing, not the artist's).
- **A citation string must never leak the sourcing pipeline's own uncertainty** ("not independently verified to primary wording," "Paste feature returned 403") **or reference this repo's other edges by id.** Two more instances found and rewritten in this pass (`underscores → 100-gecs`, `mount-eerie → stereolab`) — same hard rule as the citation-discipline entry above, still recurring.

## Known quirks / gotchas

**Never write scripts to surgically edit `seed-data.ts`.** The file previously had smart-quote (U+2018/2019) string delimiters that broke script-based parsing. It is now fully corrected to straight ASCII quotes. Edit strings directly in the file — find the artist, change the value, done.

**Module cache in `lib/graph-data.ts`.** The `let _cache: GraphData | null = null` at module level means patching `public/graph.json` has no effect until you restart the dev server (see the restart procedure in the next entry — `pkill -f "next dev"` alone is not enough).

**Restarting the dev server: `pkill -f "next dev"` does not kill the actual server process, and running it repeatedly silently accumulates zombies that corrupt the build.** `next dev` spawns a child `next-server` process that does the real work — its process name is `next-server`, not `next dev`, so a pattern-match kill on `"next dev"` leaves it running. Do this enough times in one session (e.g. once per `public/graph.json` restart) and you get several `next-server` processes simultaneously writing to the same `.next` directory, which corrupts Turbopack's chunk manifest: the HTML one process serves ends up referencing a CSS/JS chunk hash a *different* still-running process no longer has, so the asset 404s — the page loads but comes back completely unstyled (this is exactly what "you broke all the genre/scene/artist pages" turned out to be, once). The correct restart is `ps aux | grep next` to find every `next-server`/`next dev` PID (not just what one `pkill` pattern catches), `kill <pids>` (or `kill -9` if they don't die), then `rm -rf .next` before `npm run dev` again — the cache wipe matters as much as the process kill once corruption is already suspected. If a page loads with no styling at all, check for exactly this before assuming a CSS/code regression.

**Never run `npm run build` while the dev server is running, and never trust "the build passed" as evidence the browser sees your change.** Both write into `.next`, and the collision has a *silent* variant of the quirk above: instead of a 404 and an unstyled page, the served HTML keeps referencing a chunk that still exists on disk but predates your edit, so the page renders perfectly using old code. Three consecutive canvas changes were reported as "no change / still the same" this way, and each time the reflex was to assume the values were wrong and change more code. Symptoms: `tsc`/`lint`/`build` all clean, the source visibly contains the edit, and the page is unchanged. Use `tsc --noEmit` + `eslint` during a session and save the production build for after the dev server is stopped.

**Verifying a change actually reached the browser is a three-level chase, not a grep of the page HTML.** `ForceGraph` is `dynamic(..., { ssr: false })`, so the served HTML lists neither it nor its code — the chain is `app_(graph)_layout_tsx_*` -> a ~700-byte `components_graph_ForceGraph_tsx_*` stub -> the ~280KB implementation chunk. Grepping the HTML's own chunk list finds only unrelated chunks and proves nothing (this produced a confidently wrong diagnosis once). Follow the stub chain, then grep the implementation chunk for something the bundler cannot inline away — a numeric constant used in arithmetic works, a bare `const NAME = 0.42` does not, since those are substituted at their use sites.

**Before changing a rendering value because "it doesn't look different," compute what it currently renders at.** The node-glow work burned three rounds on radius and threshold changes while the actual halo alpha sat at `0.044` — 11/255 on screen, against Velvet Underground's 179/255. No radius change can make a 4%-alpha glow visible, and the fix was a one-line alpha change once the number was actually measured. Multiplied chains like `GLOW_INTENSITY * scoreBrightness * cloudDotFade * dimFactor` collapse to far less than any single factor suggests, so evaluate the whole product for a representative node before touching anything.

**Next.js 16 breaking changes.** Read `node_modules/next/dist/docs/` before touching routing or server/client component boundaries. `dynamic` with `ssr: false` is NOT allowed in Server Components — use a plain import instead.

**No `'use client'` on graph routes.** The `(graph)` layout is a Server Component shell; only the canvas-based `ForceGraph` and search/filter components are Client Components.

**`react-force-graph-2d`'s `minZoom`/`maxZoom` are declarative-only.** They're not in the ref's imperative `methodNames` — you can't call `fgRef.current.minZoom(...)`. To change zoom bounds at runtime, swap which prop value is passed via React state instead.

**Never reconstruct a `CanvasGradient` per node per frame.** With `autoPauseRedraw={false}` (required for the zoom-based cloud/detail reveal, see Architecture decisions above), the whole canvas repaints every frame regardless of physics state — any per-node gradient/glow must be a pre-rendered offscreen-canvas sprite reused via `drawImage`, or it's a severe, easy-to-reintroduce lag regression (this happened once already, from a star-twinkle effect).

**Never call `fetch()` directly in `scripts/build-graph.ts` — always go through `fetchWithTimeout()`.** Plain `fetch()` has no timeout; if iTunes/Deezer/MusicBrainz/Cover Art Archive accepts the connection and never responds (observed directly — MusicBrainz/CAA started silently going quiet instead of returning 429 after ~7 `build:data` runs in one session), the whole pipeline hangs forever with no error, no timeout, nothing in the log past the last `console.log`. `fetchWithTimeout()` wraps every call with an 8s `AbortController` cap so a bad response degrades to a missing cover/image instead of an indefinite hang.

**Restarting the dev server mid-session (e.g. after a route-group move) can produce a confusing "page loads with something missing, hard reload freezes ~2s then it's fine" symptom that looks like a data bug but isn't.** Two things compound: (1) `next dev` (Turbopack) compiles routes on-demand — the first hit to any route after a restart pays a real compile cost, which is the ~2s freeze; (2) a browser tab that was already open and connected to the old process's HMR websocket can render a client-side navigation from stale state until a hard reload forces a genuinely fresh request. If a user reports this, check whether the data itself is actually correct in `public/graph.json`/`seed-data.ts` first (it usually is) before assuming a real bug — this is dev-mode session churn, not a production-reachable issue.

**American-underground lineage palette** (`AMERICAN_UNDERGROUND_LINEAGE_COLORS`, amber/orange/rust family, hue ~18–22° — deliberately held to orange-rust rather than drifting toward core's gold at ~42°): noise-alt `#7A3418` (deepest) → college-rock `#B85C2E` → indie-rock `#E8834A` (lightest).
